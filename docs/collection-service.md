# 集合召回采集服务设计

面向资料集合（而非单次原文读取）的召回采集层，运行在本地模拟冷归档来源之上。所有时间均为可推进的虚拟时钟，不依赖真实冷存储等待。

## 要解决的问题

1. 旧程序每次查询都重新提交召回，同一卷资料反复排队。
2. 一个大集合长期占满热存储配额，小请求被饿死。
3. 共享资料的请求取消后，已就绪的临时副本无人领取，白占热存储；排队中的任务无法撤回，完成通知可能迟到。
4. 调用超时可能其实已经排队，盲目补发会制造重复任务；持续故障时又不能无限重试。
5. 临时副本到期或资料换版后，必须能说清哪些字节已可靠保存，重新准备不能把另一版资料接到旧进度后面。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `src/source.mjs` | 本地冷归档来源：虚拟时钟、介质目录、配额准入、20 秒 TTL、幂等 `/recall`，以及 `dropRecall`/`rejectRecall`/`blockData`/`bumpVersion` 故障与演进注入。 |
| `src/client.mjs` | 来源 HTTP 客户端。区分 `timeout`/`network`/`http` 错误，调用方据此判断“可能已在途”。 |
| `src/planner.mjs` | 纯函数规划：需求画像、按介质切配额内批次、优先级/截止/体积排序、老化提权、阻塞原因。 |
| `src/service.mjs` | 采集服务：请求与需求登记、共享去重、提交与幂等重试、状态核查、领取落盘、取消复核、到期/版本处理、容量计费、馆员队列视图。 |
| `src/vault.mjs` | 可靠保存库：按 `资料/版本` 隔离，临时文件 + 原子 rename，清单记录字节数与 sha256，旧版进入 `quarantine/`。 |
| `src/demo-collection.mjs` | 四个虚拟时钟演示场景。 |
| `test/collection.test.mjs` | 规划器单测与服务端到端集成测试。 |

## 关键决策

### 1. 需求与作业两级模型，共享资料只挂一个在途作业

- `request`（采集请求，含优先级与截止时间）拆成多条 `need`（单项资料需求）。
- 同一资料的多条 need 指向同一个召回作业；新请求受理时，若资料已被存活作业覆盖，不再提交。
- 作业身份由 `介质 + 资料id@版本 + 代次` 哈希生成（`recall-<media>-<hash>-g<gen>`），同身份提交在来源与服务两侧都是幂等的。

### 2. 公平调度，防止大集合饿死小请求

- 单卷一次挂载可带多项：规划器先按介质分组，再切成不超过配额的批次。
- 排序键：优先级档 → 截止时间 → 批次体积 → 次序。小而急的批次自然排在前面。
- 被配额阻塞的候选累计 `aging`，每阻塞 3 轮优先级提升一档，任何候选最终都能被选中；阻塞原因与等待轮次进入馆员视图。
- 已就绪副本领取落盘后立即释放热存储，被阻塞批次在下一轮对账自动获得配额，无需人工干预。

### 3. 超时/故障：可能已排队，就绝不换号补发

- 提交失败（超时、503、连接中断）时作业保持 `submitting`，使用**同一 requestId** 幂等重试，最多 3 次。
- 重试间隙通过 `GET /jobs/:id` 核查：来源能查到就以来源状态为准（转为可查证的 `queued`/`ready`），查不到且从未确认在途，达到上限后标记 `failed` 并停止补发，交馆员人工处理。
- 指标区分“提交尝试次数”（可能已到达来源）与“确认挂载数”，来源侧任务数可直接核对。

### 4. 取消与迟到完成

- 取消请求只终结其 need；随后做共享复核：资料若仍被其他请求需要，作业保留。
- 作业全部资料无人需要时：`ready` 立即调 `DELETE` 释放热存储；`queued` 无法撤回，标记 `orphaned`（迟到完成候选），不新建任何任务。
- 迟到的 `ready` 通知到达后，服务识别孤儿作业，不做无意义领取，直接释放并计入 `lateReleases`。

### 5. 到期与版本：字节边界必须可查证

- 临时副本 20 秒到期：作业标记 `expired`，资料签名代次 +1，重新准备使用新作业身份（`g1`、`g2`…），旧作业不再续接。
- 目录版本推进：旧版已存字节整体移入 `quarantine/` 并改名留痕；新版本以新签名独立召回、独立落盘。
- 领取时校验返回版本必须等于作业就绪时的版本快照，不符则拒绝写入。
- 每份落盘资料附带 manifest（版本、字节数、sha256、保存时刻、来源作业号），blob 与 manifest 通过临时文件原子提交。

### 6. 虚拟时钟与容量计费

- 来源是时钟权威：`advance(n)` 先在当前时刻完成一次调度对账，再推动来源 n 个虚拟秒，然后对新时刻再对账，保证 t 时刻受理的请求挂载后 `readyAt = t + 准备时长`。
- 热存储按 `就绪占用体积 × 推进秒数` 累计 `hotUnitSeconds`；提前释放即停止累计。

## 馆员队列视图

`renderQueue()` / `snapshot()` 给出三类信息：

- **当前阻塞**：每个未完成请求的阻塞项（资料状态、作业号、作业状态、原因说明），以及热存储预留/剩余。
- **预计下一动作**：带时间点的待办（轮询、领取、重试、重准备、人工介入）。
- **资料完整度**：每项请求的 `已保存项/总项`、字节进度与可视化进度条；可靠库 manifest 与隔离区可逐字节核对。

## 演示场景（`npm run demo:collection`）

1. `quota`：配额耗尽下小急件插队先完成，阻塞大集合在配额释放后自动续上。
2. `timeout`：召回响应故障导致“可能已在途”，同身份幂等重试，来源侧始终只有一个任务。
3. `cancel`：共享请求全部取消后的迟到完成，被识别并立即释放热存储。
4. `version`：资料换版后旧字节隔离、新版独立保存，互不续写。

可通过场景名单跑，例如 `npm run demo:collection -- timeout`。
